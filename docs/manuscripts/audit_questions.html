AUDIT_QUESTIONS — Diagnostic question bank for stuck or sprawling projects

Date: 2026-04-25 Use: When a project feels off but you can't articulate why, run these questions against it. Tired-mode-compatible: most are read-and-react. Pair with /plan-runciter-audit or run standalone.

How to use

Pick ONE category that matches your hunch about what's wrong. Run those questions through the AI against the project. Capture answers in AUDIT_<project>_<date>.md. Don't act on findings tonight; review tomorrow.

Category 1 — Scope drift

When a project has grown beyond what you remember agreeing to.

  1. What was the original scope (per the earliest planning doc)? Quote it.
  2. What's currently in the project that wasn't in that scope?
  3. Which additions were deliberate decisions and which crept in?
  4. Of the additions, which earned their keep? Which didn't?
  5. If I deleted everything outside the original scope, would the project still be valuable?
  6. Is there a decision log? If not, what should retroactively go in it?
  7. What's the smallest version of this project that still does the core thing?
  8. What was I hoping the additions would do, and did they do it?

Category 2 — Architecture decay

When the code feels harder to reason about than it used to.

  1. Where in the codebase do I keep "looking up the same thing"? That's where mental load is highest.
  2. Which files have been touched most often in the last 3 months? git log --name-only then count.
  3. Are there files that should change together but live apart?
  4. Are there modules that do too much, or modules that exist only to forward calls?
  5. What's the thing I'd do differently if I started over right now?
  6. Of those things, which are cheap to fix retroactively? Which would require rewriting?
  7. Is there a circular dependency I've been routing around?
  8. Where do I have try/except that I added because something failed once?

Category 3 — Documentation drift

When docs don't match the code.

  1. Pick 3 random sections of CLAUDE.md. Are they still true?
  2. Is there a doc that was important once and is now irrelevant?
  3. Are there terms in docs that I now use differently in code?
  4. What's been added to the project that no doc mentions?
  5. What's deprecated in the docs but still in code?
  6. Are the README's "how to run" instructions accurate today?
  7. Do my code comments contradict my prose docs anywhere?
  8. Which docs would be embarrassing if a stranger read them?

Category 4 — Energy mismatch

When the project is taking more energy than it's giving back.

  1. When was the last session where I left feeling good?
  2. What in the project still excites me? What feels obligatory?
  3. If I could outsource one part of this project, which part?
  4. Is there a part of this I keep avoiding? What is it telling me?
  5. Have I been working on parts that don't matter because they're easier?
  6. What's the smallest thing that would re-spark my interest?
  7. Is this project competing with something else for my attention?
  8. What's the ratio of time spent thinking-about vs. working-on?

Category 5 — AI-coding fragility

When sessions with the AI keep producing wrong-feeling output.

  1. How much context do I load before doing any work? Is it under 30% of my window?
  2. Where does the AI consistently get something wrong on this project? What do those mistakes have in common?
  3. Are there facts in this project that exist in 3+ places (docs, code, memory)? Which is canonical?
  4. Are there fixtures? Can I verify any output against expected?
  5. When the AI proposes a change, can I test it cheaply, or do I have to read and judge?
  6. What does my smoke test look like? If "doesn't have one" — that's the audit answer.
  7. How often does the AI duplicate work because it doesn't know the existing function?
  8. Is there an index/routing doc, or does the AI grep blindly?

Category 6 — Dependency rot

When the boring stuff stops working.

  1. When did I last update dependencies? pip list --outdated.
  2. Is there a requirements.txt (or pyproject.toml, package.json) that matches what's installed?
  3. Are there hardcoded paths that would break on another machine? grep "C:" -r .
  4. Does the project have a .python-version or equivalent?
  5. Are there scripts that work-only-by-luck?
  6. What's the oldest piece of code in this project? Should it stay or be rewritten?
  7. Are there imports that aren't used?
  8. Are there packages I'm depending on that have alternatives I should consider?

Category 7 — The "is this still mine" check

Every project should still feel like it belongs to you.

  1. Could I explain this project to a friend without notes?
  2. Do I know why each file exists?
  3. Do I remember writing the code, or does it feel alien?
  4. Is there a file I'm afraid to touch?
  5. Is there architecture I inherited from the AI that I don't actually understand?
  6. What would I do if all the AI assistance disappeared tomorrow?
  7. Have I been following the AI's suggestions or my own taste?
  8. What do I want this project to become that I haven't admitted yet?

Category 8 — Closure readiness

When you suspect a project is done but haven't said so.

  1. What hasn't changed in the last 3 months that you keep planning to change?
  2. What part of the project would still be valuable if you stopped today?
  3. What would have to be true for you to say "this is done"?
  4. Is "done" actually attainable, or is it a moving target?
  5. If a friend asked what this project does, what's the cleanest answer?
  6. What would freezing this project look like in concrete terms?
  7. What's the cost of keeping it active vs. freezing it?
  8. Could parts be salvaged into another project if you froze the whole?

- [things I didn't expect to be problems but are]

  - ...

  - ...
